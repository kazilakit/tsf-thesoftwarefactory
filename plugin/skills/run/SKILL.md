# Run one factory step

Run exactly one step of one task, then stop. Only the core moves tasks; you relay its output and dispatch the stage agent. Never retry a failed command and never change anything to work around a failure.

Ground rules: never write vault notes, journals or memory, even if a CLAUDE.md asks for it; never touch the user's checkouts; never push. The guard still enforces this.

For factories with a `github` block the core pushes task changes to GitHub after each step; the agent does nothing for it.

A claimed step is always run. Once `next` has returned a ticket, the step belongs to this invocation. Always run it (step 4 for check and ship, step 5 for agent steps). Never skip, change or stop a claimed step because of what the task, `context.feedback` or the owner's answer says. Pass the answer and feedback to the agent word for word; the agent decides what they mean for its stage, for example by returning blocked with a question. The only exits after a claim are the agent-error path and a `complete`, `check` or `ship` error reported as it is. Cancelling or pausing a task is the owner's Board action. If the owner seems to want that, say so in one line after the step has finished, for example "the answer asks to cancel T-n; cancel it on the Board". Never instead of running the step.

This session's id is `${CLAUDE_SESSION_ID}`. The factory root, written `<root>` below, is the path `printenv FACTORY_ROOT` prints in step 0: replace `<root>` with the printed path. The CLI is `HUSKY=0 node "<root>/core/dist/cli.js"` (the core must be built); the `HUSKY=0` prefix keeps the repos' git hooks out of the core's git work. It takes the store from the `FACTORY_STORE` environment variable (`local` by default, or `factory-app`; `file` and `blocks` are still accepted), so pass no store flag. `FACTORY_STORE_LOCAL_PATH` moves the store data only. Write each command out in full with these values; do not use shell variables or command substitution. Put every path argument in double quotes. Every `complete`, `check` and `ship` command passes `--factory "<context.factory.factoryId>"` with the ticket's factory id, so it uses the same store as `next` (a local factory always uses the local store).

0. Run `printenv FACTORY_ROOT`. If it prints nothing, reply `factory: factory root not found or session env missing; set FACTORY_ROOT or restart the session` and stop. Then run `printenv FACTORY_CLAIMANT`. Unless its output ends with `:` followed by the first 8 characters of `${CLAUDE_SESSION_ID}`, reply `factory: session env missing; restart the factory session` and stop.
1. Set `mode` to `loop` if `$ARGUMENTS` contains `--loop`, otherwise `session`. A word in `$ARGUMENTS` that starts with `T-` followed by digits (`T-<n>`) names one task: set `task` to the first such word. Any other word that is not a flag is a factory id: set `factory` to it and pass it as `--factory "<factory>"`, always double-quoted. It must match `^[a-z][a-z0-9-]{0,39}$`; if it does not, reply `factory: bad factory id` and stop. One factory per `/factory:run` (the CLI's `--factory` can repeat, but this skill passes one). With neither, `next` considers every active factory.
2. Run `HUSKY=0 node "<root>/core/dist/cli.js" --mode <mode> next [task] [--factory "<factory>"] --json`. Leave out `[task]` and `[--factory "<factory>"]` when they are not set. If the output is `nothing to do`, reply `factory: nothing to do` and stop. If the output contains ` is waiting on `, reply `factory: <output>` and stop. If the output is `paused`, reply `factory: paused` and stop. If the output is `inactive`, reply `factory: inactive` and stop. If the output is `no factories; run ./factory init`, reply `factory: no factories; run ./factory init` and stop. If the command fails, show its stderr in one line and stop. The core also pulls GitHub changes before `factory next`; a `github:` line on stderr is informational and needs no action from you. The JSON ticket is `{taskId, step, worktree, runId, model?, context: {task, factory: {factoryId, name, docsPath}, checks, spec?, plan?, feedback?, checksReport?}}`. `model` is present only when the factory set a model for this stage.
3. Write the session file `<root>/runs/.sessions/${CLAUDE_SESSION_ID}.json` with the Write tool, as `{"taskId": ..., "step": ..., "worktree": ..., "mode": <mode>, "session": "${CLAUDE_SESSION_ID}", "factory": <context.factory.factoryId>}`. `step` is the ticket's `step` as it is; `factory` is the ticket's `context.factory.factoryId`, so the claim renewal uses the same store. From here on, every path out of this skill, failures included, ends by deleting that file with `rm -f "<its literal path>"`.
4. If `step` is `check`, run `HUSKY=0 node "<root>/core/dist/cli.js" --mode <mode> check <task> --factory "<context.factory.factoryId>"` with the Bash tool's `timeout` set to `600000`. If it is `ship`, run `HUSKY=0 node "<root>/core/dist/cli.js" --mode <mode> ship <task> --factory "<context.factory.factoryId>"`, also with `timeout` `600000`. Print the CLI's line, delete the session file and stop.
5. Otherwise the step is an agent step. Pick the agent from the step: `spec` is `factory:spec-writer`, `plan` is `factory:planner`, `build` is `factory:implementer`, `verify` is `factory:verifier`, `review` is `factory:reviewer`. First delete any old reply with `rm -f "<root>/runs/<task>/<step>.reply.md"`, so a stale reply is never recorded. Then call the Agent tool in the foreground (`run_in_background: false`) with that `subagent_type` and a prompt that holds the items below. If the ticket has `model`, also pass it as the Agent tool's `model` parameter; if it has none, leave the `model` parameter out, so the agent keeps the session's model. The prompt holds:
   - the task's title and description (`context.task`);
   - the worktree path, as the place to work and read, with these rules written out: the agent does not start in the worktree, so every Bash command starts with `cd "<worktree>" &&` or uses `git -C "<worktree>"`; every Grep and Glob call passes `path: "<worktree>"`; Read uses absolute paths under the worktree;
   - `context.spec`, `context.plan`, `context.feedback` and `context.checksReport`, whichever are present. Copy the owner's answer and the feedback into the prompt word for word, and always dispatch the agent, whatever they say;
   - for `build` only: the repo's check commands, copied from `context.checks` (each check with its folder and command);
   - for `spec` only: the background docs folder, `context.factory.docsPath`, as an absolute path to read, read-only. If it is empty, say in the prompt that there are no background docs.

   For `review`, give the reviewer only the spec, the output of `git -C "<worktree>" diff origin/<context.task.baseBranch>...HEAD`, and the worktree path as a read-only root for understanding the code the diff touches, with the Grep, Glob and Read rules above. Nothing else.
6. Record the agent's reply.
   - If the Agent tool reports that the agent is still running, wait for it to finish before going on.
   - If the Agent call errored, or returned no final message from the agent, do not run `complete`. Delete the session file, print `factory: agent error: <one line>; re-run /factory:run <task> to retry` and stop.
   - The SubagentStop hook writes the reply file `<root>/runs/<task>/<step>.reply.md`. If it is missing, write the text the Agent tool returned to that path with the Write tool, copied unchanged. Never compose or edit a reply, even one that looks malformed; the core handles a malformed reply.
   - Read the reply file and look for both `<factory-result>` and `</factory-result>`. If either is missing, the agent forgot its result block: ask that same agent at most once, with SendMessage to the agent's id from the Agent call, and this exact message, word for word: "Your reply ended without the `<factory-result>` block, so the factory cannot record this step. Do not redo, change or add any work, and do not run any tool. Reply again with your final reply only, in the reply format: the same summary, the `<factory-result>` JSON block and, if your stage writes a doc, the `<factory-doc>` block." Wait for its answer. The restated reply replaces the reply file by the SubagentStop hook, as before; if the reply file did not change, write the restated text the agent returned to it with the Write tool, copied unchanged. If the SendMessage call fails, leave the reply file as it is. Do not ask a second time: run `complete` whatever the reply file holds, and the core blocks the task if it is still malformed.
   - Run `HUSKY=0 node "<root>/core/dist/cli.js" --mode <mode> complete <task> <step> --reply "<root>/runs/<task>/<step>.reply.md" --factory "<context.factory.factoryId>"`.
7. Print the CLI's line (for example `T-12 spec_review`), delete the session file and stop. One step per invocation. If `complete` reports a `ClaimError` or a `StageError`, report it as it is, delete the session file and stop; do not retry.
